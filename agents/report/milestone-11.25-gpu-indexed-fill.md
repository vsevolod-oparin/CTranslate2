# M11.25 — GPU Indexed Fill Kernel

## Summary

Moved `indexed_fill` from a CPU scatter loop to a GPU compute kernel. The kernel runs as an encode-only operation (no `commit_and_wait()` after it), with `protect_buffer()` deferring the index buffer's recycling until the next sync. A pre-sync (`CT2_COMMIT_AND_WAIT()`) before the kernel is still required to flush prior GPU writes to the logits buffer before the scatter kernel executes.

## Problem

`indexed_fill` is called by `DisableTokens::apply()` in `src/decoding_utils.cc` during beam search and greedy decoding. It writes a disable value (typically `-inf`) to specific positions in the logits tensor. The original implementation was a CPU loop (`std::fill`-style scatter) that required `CT2_COMMIT_AND_WAIT()` to flush GPU-written logits to shared memory before CPU could read/write them. This sync was measured at ~38% of CPU time in whisper inference profiling.

```
Before:  indexed_fill() → CT2_COMMIT_AND_WAIT() → CPU loop: x[indices[i]] = val
After:   indexed_fill() → protect_buffer(indices) → CT2_COMMIT_AND_WAIT()
                         → GPU scatter kernel (encode-only)
```

The CPU path generated **1477 `commit_and_wait()` syncs** per whisper-large-v3-turbo inference (beam_size=5, 60s audio) — visible in the M11.23 sync trace as the second-largest contributor after `synchronize_stream`.

## Solution: GPU Scatter Kernel

### MSL Kernel

New file `src/metal/kernels/indexed_fill.metal` — one thread per index, trivially parallel:

```metal
#define DEFINE_INDEXED_FILL(T)                                           \
  kernel void indexed_fill_##T(                                          \
      device       T*       x        [[buffer(0)]],                      \
      constant     T&       fill_val [[buffer(1)]],                      \
      device const int*     indices  [[buffer(2)]],                      \
      uint gid [[thread_position_in_grid]])                              \
  { x[indices[gid]] = fill_val; }
```

Instantiated for `float`, `half`, `int`, `short`, `char`, `bfloat` (guarded by `__HAVE_BFLOAT__`).

### Infrastructure

Standard Metal kernel infrastructure following the M4.2 pattern:

| Component | Implementation |
|-----------|---------------|
| MSL source | `kIndexedFillMSL` in `msl_strings.h` (generated by `gen_msl_strings.py`) |
| Library cache | `compile_library_once(flag, lib, kIndexedFillMSL, "indexed_fill")` |
| PSO cache | `PSOCache::get(get_indexed_fill_library, name)` |
| Kernel name | `indexed_fill_<MetalTypeName<T>::value>` |

### Host-Side Encoding

```objc
metal::protect_buffer(indices);         // defer index buffer recycling
CT2_COMMIT_AND_WAIT();                  // flush prior GPU writes to logits

char kname[kKernelNameBufSize];
std::snprintf(kname, sizeof(kname), "indexed_fill_%s", MetalTypeName<T>::value);
id<MTLComputePipelineState> pso = get_indexed_fill_pso(kname);

NSUInteger x_off = 0, idx_off = 0;
id<MTLBuffer> x_buf   = metal_buffer_for_ptr(x, &x_off);
id<MTLBuffer> idx_buf = metal_buffer_for_ptr(indices, &idx_off);

id<MTLComputeCommandEncoder> enc = metal::create_compute_encoder();
[enc setComputePipelineState:pso];
[enc setBuffer:x_buf   offset:x_off   atIndex:0];
[enc setBytes:&a       length:sizeof(T) atIndex:1];
[enc setBuffer:idx_buf offset:idx_off atIndex:2];
[enc dispatchThreads:MTLSizeMake(ct2_u32(num_indices), 1, 1)
   threadsPerThreadgroup:MTLSizeMake(
       std::min<NSUInteger>(ct2_u32(num_indices),
                            pso.maxTotalThreadsPerThreadgroup), 1, 1)];
[enc endEncoding];
[enc release];
```

No `commit_and_wait()` after encoding — the kernel result is consumed by subsequent GPU work in the same command buffer.

## Buffer Protection Pattern

The index buffer is a temporary `StorageView` created by `DisableTokens::apply()` — it gets freed immediately after the call returns. Since `indexed_fill` is now encode-only, the GPU has not yet read the buffer when it is freed. Without protection, the buffer returns to the allocator's reuse pool and may be overwritten before the GPU executes the kernel.

```
DisableTokens::apply()
  |-- Creates temporary StorageView with flat_indices on Metal device
  |-- Calls primitives<METAL>::indexed_fill()
  |     |-- protect_buffer(indices)     <- defer index buffer recycling
  |     |-- CT2_COMMIT_AND_WAIT()       <- flush prior GPU writes to logits
  |     |-- Encode GPU scatter kernel   <- encode-only, no sync after
  |     +-- return
  +-- Temporary StorageView freed -> goes to _pending_free (protected)
        +-- Recycled at next commit_and_wait()
```

`metal::protect_buffer(indices)` sets the `gpu_protected` flag on the allocation's `_live` map entry. When `free()` is called, the buffer moves to `_pending_free` instead of the reuse pool. `flush_pending_frees()` (called by `commit_and_wait()`) releases it back to the pool after the GPU has completed.

## Pre-Sync Requirement

A `CT2_COMMIT_AND_WAIT()` before the GPU kernel is still needed. Without it, float32 inference (whisper-base) produces garbage output — the scatter kernel operates on logits that have stale data from uncommitted prior GPU work. Float16 inference (whisper-large-v3-turbo) works without the pre-sync, but float32 does not.

| Configuration | Without pre-sync | With pre-sync |
|---------------|-----------------|---------------|
| float16 (whisper-large-v3-turbo) | Correct output | Correct output |
| float32 (whisper-base) | Garbage output | Correct output |

The exact cause is not fully understood. Possible explanations:

1. **MPS GEMM vs custom compute encoder ordering**: The logits are produced by an MPS GEMM (which uses its own internal command encoder). The indexed_fill custom compute encoder may not have implicit ordering guarantees with prior MPS work on the same command buffer.
2. **CPU write visibility**: The indices buffer is filled by CPU writes. The `commit_and_wait()` may serve as a memory barrier ensuring CPU writes to the shared-memory buffer are visible to the GPU.

This means the original `CT2_COMMIT_AND_WAIT()` sync point is preserved — the goal of eliminating the 38% CPU bottleneck was **NOT** achieved in this milestone. The infrastructure is in place for future optimization if the ordering issue can be resolved.

## Dead Code Cleanup

Removed `has_pending_gpu_work()` and the `_has_pending_encode` tracking flag from `utils.h`/`utils.mm`. These were introduced as part of an allocator-level deferred-free approach that checked `has_pending_gpu_work()` in `free()` to defer ALL buffer recycling during encode-only sequences. This caused memory pool starvation and massive regression (3x to 0.8x). The targeted `protect_buffer()` approach replaced it, making these symbols dead code.

## Attempted Approaches That Failed

### 1. Allocator-Level Deferred Free

Set `_has_pending_encode = true` on every `create_compute_encoder()` call, then checked `has_pending_gpu_work()` in `free()` to defer ALL buffer frees during any encode-only GPU work.

| Metric | Before | With allocator-level defer |
|--------|--------|---------------------------|
| Metal speedup | 3.17x | 0.41x |
| Pool reuse | Normal | Starvation (all buffers stuck in _pending_free) |

Reverted to targeted `protect_buffer()` which only defers the specific buffers that are GPU-referenced.

### 2. Encode-Only Without Pre-Sync

Removed `CT2_COMMIT_AND_WAIT()` before the GPU kernel to eliminate the sync entirely.

| Model | Precision | Result |
|-------|-----------|--------|
| whisper-large-v3-turbo | float16 | Correct |
| whisper-base | float32 | Garbage (wrong tokens, infinite loops) |

Root cause unclear — possibly MPS GEMM (which writes logits) and the custom compute kernel have ordering guarantees that differ between precision modes, or CPU write visibility semantics differ for shared-memory buffers.

## Performance Impact

Speed benchmarks are variable across runs. The pre-sync is preserved, so this milestone does not reduce sync count — the work is moved from CPU to GPU but the sync barrier remains.

| Run | CPU (ms) | Metal (ms) | Speedup |
|-----|----------|------------|---------|
| test_faster_whisper run 1 | 25359 | 10813 | 2.35x |
| test_faster_whisper run 2 | 27301 | 8006 | 3.41x |
| test_faster_whisper run 3 | 17761 | 12740 | 1.39x |
| test_whisper (float32) | 5873 | 2392 | 2.46x |

The `test_faster_whisper` variance (1.39x–3.41x) is caused by `faster_whisper`'s seek loop generating different numbers of total tokens per run due to MPS GEMM floating-point non-determinism (see M11.27 report for full analysis). The `test_whisper` (raw CTranslate2 API, float32) result of 2.46x is the reliable measurement. With the pre-sync preserved, the sync trace remains unchanged from M11.23:

```
   1509  devices.cc:162          (synchronize_stream)
   1477  primitives_memory.mm:95 (indexed_fill — pre-sync preserved)
     16  primitives_gemm.mm:1161 (CPU cblas)
   ----
   3002  total
```

## Future Work

1. **Investigate float32 vs float16 pre-sync requirement**: Understanding why float32 requires the pre-sync while float16 does not would potentially allow eliminating the `CT2_COMMIT_AND_WAIT()` entirely — unlocking the full 38% CPU bottleneck elimination (1477 syncs).

2. **Fuse indexed_fill into softmax kernel**: Rather than a separate scatter pass, write `-inf` directly during the softmax reduction. This would eliminate both the indexed_fill kernel dispatch and its sync point entirely.

3. **MTLFence or MTLEvent ordering**: If the root cause is MPS-to-compute encoder ordering, a `MTLFence` between the MPS GEMM encoder and the indexed_fill compute encoder might provide the necessary ordering guarantee without a full `commit_and_wait()`.
